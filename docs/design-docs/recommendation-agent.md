# 设计：推荐 Agent、问答 Agent 与模型接入

- **状态**：草稿，待评审
- **日期**：2026-10-12
- **关联**：`docs/design-docs/data-model.md`、`docs/product-specs/daily-recommendation.md`

## 1. 核心原则

1. **硬约束由代码保证，不交给模型。** 过敏原、忌口、饮食方式、厨具、时间在 SQL 层过滤；模型输出回来后再用代码校验一遍。模型只负责在合法候选中挑选、搭配、写理由。
2. **模型输出一律经过 schema 解析。** 用 JSON Schema 结构化输出，回来后用 zod 解析；解析失败就带着错误信息重试一次，再失败就走降级。
3. **模型不可用时也能推荐。** 每日推荐有纯规则的降级路径，问答则明确提示暂时不可用。
4. **少发个人数据。** 发给模型的只有口味档案的结构化摘要和菜谱候选，不发昵称和账号信息。

## 2. 模型接入层（LLM Gateway）

- 首版只实现 **OpenAI 兼容**接口，中转站与模型（`gpt-6.1-sol`）都在管理端配置，见 `docs/product-specs/admin.md`。
- Gateway 作为横切能力挂在 `Providers.llm` 上，接口如下：
  - `complete({ purpose, messages, schema?, tools?, signal })`：返回已经过 zod 解析的结果；
  - `stream({ purpose, messages, tools?, signal })`：问答用的流式输出；
  - `embed({ purpose, texts })`：没有配置 Embedding 模型时返回「不支持」，调用方走降级。
- 当前启用的供应商配置从 model-config 领域读取：在组合根（`apps/server/src/app.ts`）把读取函数注入 Gateway，不违反「Providers 不依赖领域」的规则。配置缓存 30 秒，管理端修改后主动失效。
- 每次调用写一条 llm_calls（不含正文）并输出结构化日志；超时默认 30 秒，网络错误与 5xx 指数退避重试最多 2 次，4xx 不重试。
- 结构化输出与工具调用的支持情况来自「测试连接」的探测结果。不支持 JSON Schema 时，退到「提示词要求 JSON + zod 解析 + 重试」。
- 提示词放在各领域 config 层的版本化文件中，prompt_version 写入 daily_plans，方便对比效果。

## 3. 每日推荐流水线（plan 领域 service 层）

```text
档案 + 近 14 天饮食/反馈
        │
        ▼
① 硬约束过滤（SQL） ──► 合法候选池（只含 published + 本人待审的菜）
        │
        ▼
② 打分排序（代码）：偏好相似度 + 喜欢/不喜欢 + 近期去重 + 多样性
        │                       每个餐次 × 角色取前若干道
        ▼
③ 模型挑选与搭配（结构化输出）：每餐选菜、写理由；候选不够时可申请生成新菜
        │
        ▼
④ 代码校验：id 必须在候选池内、角色搭配合规、硬约束复查 ──失败──► 重试 1 次 ──► 降级：按②的排名规则直接挑
        │
        ▼
⑤（可选）生成新菜：模型输出完整菜谱 JSON → 食材归一 → 派生过敏原并复查硬约束 → 以 pending_review 入库
        │
        ▼
⑥ 写入 daily_plans / plan_meals / plan_dishes，按人数换算用量后返回
```

- **打分（②）**：`score = 0.5 × 偏好相似度 + 0.2 × 口味标签匹配 + 0.2 × 历史反馈 − 近期重复惩罚 + 小随机扰动`。没有 Embedding 时，偏好相似度改用「菜系 / 口味标签 / 食材」的 Jaccard 相似度。权重写在 plan 领域的 config 层，由离线评测调优。
- **候选规模**：每个「餐次 × 角色」最多取 12 道，整天总量控制在约 60 道以内，以控制 token 和延迟。
- **新菜生成（⑤）**：每天最多 1 道，只在候选池明显不足时触发（例如某个角色可选的菜少于 3 道）。生成的菜立刻给这位用户用，但标注「AI 新菜」，并进入管理端审核队列。
- **触发时机**：App 请求当天推荐时，没有就现场生成。生成过程用 SSE 推送进度和逐餐结果，满足「3 秒内开始出现」。以后可以加夜间预生成。
- **换一道**：对单个位置重新跑 ①–④；附加要求（「不辣」「想吃鱼」）先由模型解析成结构化筛选条件，再交给 SQL，而不是只靠模型理解自然语言。

## 4. 问答 Agent（chat 领域）

- 工具调用循环，每轮最多 5 次工具调用，工具参数全部过 zod 校验：
  - `search_recipes(query, filters)`：调用与推荐相同的过滤和排序，保证硬约束同样生效；
  - `get_recipe(id, servings?)`；
  - `get_plan(date)`；
  - `swap_dish(plan_dish_id, request)`：复用推荐服务；
  - `record_feedback(recipe_id, cooked?, rating?, comment?)`；
  - `propose_profile_change(patch)`：**只生成修改提案**，由 App 展示「确认」按钮，用户确认后由 App 调用档案接口真正修改。
- 上下文包括：系统提示（范围、健康话题边界）、档案摘要、今日推荐摘要和最近 20 条消息。更早的消息先压缩成摘要再放入。
- 回复通过 SSE 流式返回给 iOS。工具执行结果以结构化事件推送，App 可以据此刷新今日推荐。

## 5. 质量保障

- **单元测试**：用假的 Gateway 返回预设输出，覆盖硬约束复查、id 越界、解析失败重试、降级路径。
- **约束评测**：随机生成 1000 份档案，跑完整流水线（模型用假实现），断言硬约束违规为 0。CI 中运行。
- **效果评测**（手动运行，接真实模型）：一组固定的代表性档案，产出推荐快照，人工比对不同 prompt_version 的效果；结果记录到 docs/generated 目录。
- **可观测性**：llm_calls 记录耗时、token 与失败；推荐写一条结构化日志，包括候选池大小、所选策略和耗时。

## 6. 中转站能力（2026-10-12 探测）

对话、JSON Schema 结构化输出、工具调用可用；**没有 Embedding 模型**，第 3 节的偏好相似度按 Jaccard 方案实现。可用对话模型包括 gpt-6.1-sol、gpt-5.4-mini 等 12 个。

## 7. 原待确认项（已由探测回答）

1. 中转站的 Base URL、接口格式（Chat Completions 还是 Responses），以及 `gpt-6.1-sol` 是否支持 JSON Schema 结构化输出和工具调用。
2. 是否提供 Embedding 模型。
3. 速率限制与计费方式，用来估算每天的推荐成本。

以上问题在拿到 API Key 后，由管理端的「测试连接」自动探测并记录到 llm_providers.capabilities，不需要人工逐项确认。API Key 只填进本地的 `.env` 或管理端，不要贴到对话里。
